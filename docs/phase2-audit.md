# Phase 2 audit

A rigorous pass over the V1 repository as a GTM engineer, a staff software engineer, a data person and a
product designer. Findings are evidence-based: each one names how it was found and what it breaks. Priorities:

- **P0** — credibility/blocking. An experienced GTM engineer would lose trust in the demo.
- **P1** — major hiring signal. Present but shallow, or explicitly requested depth that is missing.
- **P2** — polish.
- **P3** — nice-to-have.

## Method

- Read README, all `docs/`, migrations, seed, `domain/`, `services/`, `integrations/`, routes, frontend.
- Ran the stack in demo mode and traced the flagship account through every screen.
- Queried the database directly for cross-entity contradictions (14 consistency checks).
- Scripted a desktop (1440×900) + mobile (Pixel 7) pass over 21 routes including three empty states,
  recording console errors, horizontal overflow, load time and DOM size.

Automated UI health was clean: **no horizontal overflow, no page errors, no error boundaries, every page has
an `h1`** at both sizes; slowest page 2.9 s (Overview, cold).

## P0 — credibility / blocking

### P0-01 The outbound provenance chain is broken in the data
`SELECT count(*) FILTER (WHERE message_draft_id IS NOT NULL) FROM activities` → **0 of 6,643 sends.**
GTMOS's core claim is *evidence → draft → human approval → send → measured outcome*, but no activity points
at the draft that produced it, and seeded drafts are never linked to a campaign send. An interviewer asking
"show me the email that generated this reply" gets nothing. **Fix:** seed approved/ready drafts for campaign
sends and link `activities.message_draft_id`; surface "generated by draft → approved by → sent as step 2" in
the account timeline; add an integration test asserting every campaign send on the flagship has a draft.

### P0-02 The flagship narrative has holes
Kestrel Analytics today: 11 signals, 5 committee roles, research with 30 evidence items, 1 opportunity — but
**0 drafts, no experiment assignment, a single-campaign journey, and all 4 workflow runs are synthetic
history** with fabricated `{"synthetic_history": true}` step outputs. The Phase 2 brief requires one account
that demonstrates signal → … → experiment → learning with no contradictions. **Fix:** give the flagship a
real multi-touch journey (webinar → generic ICP campaign → launch campaign), enrol it in the subject-line
experiment with outcomes, link its sends to approved drafts, and make its historical workflow run a *genuinely
executed* run with backdated timestamps instead of fabricated outputs.

### P0-03 Attribution is unfalsifiable: 0 unattributed opportunities
All 77 in-window opportunities have touches, and 1,221 of 1,279 touched accounts saw exactly one campaign, so
first/last/linear/U-shaped agree to within 5% on every row except the webinar. Real attribution always has an
unattributed tail (inbound, dark social, referral) and disagreeing models. A page that shows four models
agreeing teaches nothing and looks synthetic. **Fix:** add inbound/referral opportunities with no campaign
touches, and multi-campaign journeys where first- and last-touch genuinely disagree; report the unattributed
share prominently.

### P0-04 The funnel mixes an all-time count with windowed stages
`analytics.funnel` uses *all accounts* for `prospect` (2,006) but *accounts that reached the stage in the last
90 days* for every later stage (contacted 748). The headline "37% prospect→contacted" is therefore
meaningless, and every downstream conversion is computed off a cohort that isn't a cohort. **Fix:** make the
funnel cohort-based (accounts first contacted in the window, then how far they progressed), or state the
denominator explicitly per row. This is the single most likely thing for a RevOps interviewer to catch.

### P0-05 No metric definitions anywhere
Nothing defines what "qualified" means, whether reply rate is per send / per contact / per account, what
counts as a meeting, or how MQL/SQL/SQO map to GTMOS stages. RevOps credibility rests on definitions, and
`analytics.py` silently makes choices (reply rate = replies ÷ sends) that a practitioner would want stated.
**Fix:** a metric dictionary in the semantic layer, exposed in the UI and documented.

## P1 — major hiring signal

### P1-01 Enrichment never surfaces provider disagreement
`decide()` returns `set | update | keep_existing | no_data`. When two providers return different values it
silently prefers the more confident one; there is no conflict state, no flag on the field, and nothing in the
UI. The Phase 2 brief explicitly wants disagreement handled and shown. **Fix:** detect conflicts, record them
(`conflict` on the decision plus a DQ issue when material), never silently overwrite, and show the losing
value and why in the provenance table.

### P1-02 Routing is too simple to survive a senior interview
Only two strategies exist (`user`, `pool_least_loaded`). Missing: **named/strategic accounts**, true
**round-robin**, **SLA / time-to-first-touch**, country-level territories (only region), and an explicit
**fallback queue** for unmatched accounts (today they just end up ownerless — 187 accounts, 127 of them APAC).

### P1-03 Experiments lack guardrail metrics and practical significance
Only funnel metrics are tracked (`reply, positive_reply, meeting, opportunity`). There are no **guardrail
metrics** (bounce, unsubscribe, negative reply), no **minimum detectable effect** framing, and nothing
explains why optimising reply rate alone is dangerous. A data-savvy interviewer will ask exactly this.

### P1-04 The workflow engine is under-attacked
No tests for concurrent execution of the same run, worker crash mid-run, replay of a completed run, invalid
step definitions, or dependency failure. Idempotency is claimed; concurrency is not proven.

### P1-05 CRM sync design is documented only as prose in `integrations.md`
No dedicated design document; associations, deletion behaviour, event ordering, and the three canonical
failure scenarios (CRM edited mid-sync, duplicate webhook delivery, warehouse/CRM disagreement) are not
written down.

### P1-06 Scoring has no evaluation, and heuristic vs. model is blurred
The docs say predictive power is "modest" with no analysis. Current data actually shows a monotonic
relationship (meeting rate: **B 18.5% > C 15.6% > D 6.2%**), but grade A has n=1 contacted, and excluded (X)
accounts convert at 9.7%, which needs explaining. There is no backtest, no calibration view, no statement of
what is heuristic versus what would be learned, and no discussion of leakage (engagement points feed the score
*and* the outcome).

### P1-07 The Stack Inspector reports findings but not causal chains
It separately reports "35 accounts missing employee count" and "107 unmatched routing decisions". The data
shows these are the *same story*: no employee count → no segment → no routing rule matches → high-fit account
sits unowned. Connecting them is exactly the systems thinking the role is hired for.

### P1-08 No adversarial tests for the Copilot
The architecture is right (intent → approved metric), but nothing proves it refuses "DROP TABLE", "delete all
contacts", "show me the CEO's password" or "invent revenue for last quarter".

### P1-09 Grade A is too rare to be useful
A:1, B:74, C:537, D:1,345, X:49. With one A-grade account the "Act now" list is thin and grade A cannot be
validated statistically. Either the thresholds or the score's dynamic range need revisiting — deliberately,
not by inflating outcomes.

### P1-10 No negative or disqualifying signals
Every signal type increases score. Real taxonomies include layoffs, competitor adoption, churn risk and
budget freezes. Without them, "signal detection" looks one-directional.

## P2 — polish

- **P2-01 Seed scores are not bit-reproducible.** Two resets on the same day gave A:2/B:73 then A:1/B:74,
  because scoring uses wall-clock `now` while signals are anchored to the seed date (see
  `docs/phase2-baseline.md`). A demo should not change its headline numbers between runs.
- **P2-02 Data Quality renders up to 200 issues (47k characters, 202 tables) with no pagination.**
- **P2-03 The Overview never says what GTMOS *is*.** It opens with "Command center" and metrics; a recruiter
  with 60 seconds learns nothing about the problem, the systems, or what was engineered.
- **P2-04 Signals chip counts are computed on a different filter set than the header count**, so "Last 7 days ·
  0 signals" can sit next to "All 412".
- **P2-05 Contact `lifecycle_stage` is decorative** — it is written by the seed but never drives routing,
  scoring or reporting.
- **P2-06 The account page never mentions experiments**, so the account → experiment → learning link is
  invisible where it matters most.

## P3 — nice-to-have

- **P3-01** Stuck accounts are capped at 50 with no pagination.
- **P3-02** No explicit light/dark toggle (system preference only).
- **P3-03** Contact and deal sync are mapped but never scheduled; only companies are pushed.
- **P3-04** No warehouse/dbt story, which some postings mention.

---

## What is already strong (do not regress)

- Explainable scoring with per-rule evidence and a reproducible input hash.
- The enrichment waterfall's batching, cost accounting and provenance.
- Idempotency keys, persisted step state, retries, dead letters and manual retry.
- Signed webhooks with replay protection, and the rejected-delivery fix from Phase 1.
- The HubSpot boundary (unique-property upsert, change detection, field ownership).
- Data Quality rules with audited remediation, and the Stack Inspector's evidence blocks.
- UI health: no overflow, no console errors, real empty states with recovery actions.

## Execution order

1. P0-04, P0-05 (metrics correctness and definitions) — cheapest credibility win.
2. P0-01, P0-02, P0-03 (the narrative + outbound provenance + attribution) — one seed workstream.
3. P1-06 scoring evaluation, P1-09 grade distribution.
4. P1-01 enrichment conflicts, P1-02 routing depth, P1-10 negative signals.
5. P1-03 experiment guardrails, P1-04 workflow hardening, P1-08 copilot adversarial tests.
6. P1-05 CRM sync design doc, P1-07 inspector causal chains.
7. P2 items, then README/docs rewrite and screenshots.
